ADR-001: Qdrant is the only vector engine (fail-hard, no ILIKE fallback)
--------------------------------------------------------------------------------

Context
    Echo ships pgvector (memory_semantic) but embeddings are never used for
    search; the semantic handler only runs ILIKE. The user wants a real
    vector store for KataraGnosis and a clean migration for echo memory.

Decision
    Qdrant (Rust, gRPC, go-client) becomes the single vector store. The
    memory_semantic handler is rewritten to store/search in Qdrant. There is
    NO fallback to ILIKE anywhere: if Qdrant is unreachable, operations fail
    hard (503/fatal at startup). PG memory_semantic table remains but the
    embedding column is no longer written.

Consequences
    + Semantic search actually works (real vector similarity).
    - Requires Qdrant as a mandatory dependency for KataraGnosis and echo
      memory endpoints.
    - Startup fails loudly when Qdrant is misconfigured (clear ops signal).

--------------------------------------------------------------------------------
ADR-002: Blob storage = GarageHQ (S3-compatible), client = minio-go
--------------------------------------------------------------------------------

Context
    KataraGnosis uploads PDF/markdown/text and later audio. No blob storage
    existed in Echo. PostgreSQL BYTEA bloats the DB; disk volume is not
    portable; cloud S3 adds external dependency.

Decision
    Self-hosted GarageHQ (Rust, <60MB RAM) as the S3-compatible object
    store, accessed with the standard minio-go v7 client. Bucket
    inquizitive-docs; objects keyed <user_id>/<source_id>.<ext>. Migration
    to R2/AWS S3 is a config-only change.

Consequences
    + Fits the self-hosted docker-compose stack, minimal resources.
    + S3 API compatibility future-proofs the storage layer.
    - New infra service to operate (backups, keys).

--------------------------------------------------------------------------------
ADR-003: Questions generated on demand per drill, cached in DB
--------------------------------------------------------------------------------

Context
    Two options: pre-generate a question bank at ingestion time (batch LLM
    cost up front, fast drills) vs generate per question during a drill
    (2-5s latency per question). User chose on-demand.

Decision
    Questions are generated by the LLM when a card is first served in a
    drill, persisted to the `questions` table (status=active) and reused on
    subsequent reviews. After 3 correct attempts, a card gets a regenerated
    question (new phrasing) to prevent rote memorization.

Consequences
    + No wasted LLM tokens on material never drilled.
    + Explanation + distractor labels stored at generation -> instant
      feedback on objective questions.
    - 2-5s loading state on first service; mitigated by prefetching the
      next question while the user reads feedback.

--------------------------------------------------------------------------------
ADR-004: Extend the echo backend (no separate Go service)
--------------------------------------------------------------------------------

Context
    KataraGnosis needs auth, tiers, DB, prompt templates, provider config —
    all already owned by the echo backend.

Decision
    KataraGnosis is implemented inside backend/ (handler/service/
    repository/katara + worker + pkg/garage + pkg/qdrant). A separate Go
    service would duplicate auth/DB setup for no gain.

Consequences
    + Reuses JWT auth, tier service, prompt_templates/studio, settings
      provider config, observability.
    - KataraGnosis endpoints share the echo deployment lifecycle
      (acceptable for a personal monorepo).

--------------------------------------------------------------------------------
ADR-005: Standalone Next.js app at frontend/KataraGnosis (port 3002)
--------------------------------------------------------------------------------

Context
    The echo web app is an agent-orchestrator UI; KataraGnosis is a
    different product. User requested a separate project folder.

Decision
    New standalone Next.js 16 app at frontend/KataraGnosis (port 3002)
    talking to the echo backend via its own BFF proxy layer with httpOnly
    cookie auth (CORS already allows :3002).

Consequences
    + Clean product separation; can be deployed independently (e.g.,
      Vercel) later.
    - Duplicates auth UI, api-client, and UI kit scaffolding — copied
      deliberately from frontend/web to stay consistent.

--------------------------------------------------------------------------------
ADR-006: Background jobs on Asynq over Redis
--------------------------------------------------------------------------------

Context
    Ingestion (PDF extract -> chunk -> tag -> embed -> index) and weekly
    synthesis are slow, LLM-bound work. Echo had no queue.

Decision
    Asynq (github.com/hibiken/asynq) over the existing Redis: task types
    ingest_source, reprocess_source, weekly_synthesis; in-process server
    goroutine; retries with backoff; job table in PG for UI visibility and
    idempotency.

Consequences
    + Battle-tested queue with retries/periodic tasks, minimal code.
    - Redis becomes mandatory for KataraGnosis (fail-hard).

--------------------------------------------------------------------------------
ADR-007: TipTap v2 for the Notion-like editor
--------------------------------------------------------------------------------

Context
    The library needs block editing (notes, manual flashcards). Options:
    BlockNote (fastest Notion-like, API churn) vs TipTap (stable, modular).

Decision
    TipTap v2 with StarterKit + placeholder + link + task lists + tables +
    typography, wrapped in a custom toolbar + slash menu matching the
    design system.

Consequences
    + Stable API, React 19 compatible, full control of styling.
    - More assembly than BlockNote (acceptable; UI kit is custom anyway).

--------------------------------------------------------------------------------
ADR-008: Embedding service is provider-agnostic
--------------------------------------------------------------------------------

Context
    Embedding generation did not exist. The user's chat provider
    (opencode-go) likely lacks /v1/embeddings; Gemini works and is used in
    the previous inquizitive prototype; local LM Studio is an option.

Decision
    A general embedding service (service/katara/embed.go) supports
    providers via env: EMBEDDING_PROVIDER=gemini|openai-compatible, with
    base_url/api_key/model overrides. Exposed as POST /api/v1/internal/
    embeddings (Service JWT) so the agent can reuse it later.

Consequences
    + Swappable without code changes; local (LM Studio) or cloud (Gemini)
      both supported.
    - Embedding dimension is provider-dependent; switching provider
      requires re-embedding all flashcards (reprocess_source).
