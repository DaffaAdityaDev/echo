# KataraGnosis System Architecture

> Blueprint for the standalone KataraGnosis learning and test preparation application.

---

## 1. High-Level Topology

KataraGnosis operates as a standalone application within `app/KataraGnosis/` with its own dedicated backend service, database, and vector store. The primary Echo backend acts solely as an agent harness and is **not involved** in Katara's operational loop.

## 3. Data Flow & Subsystems

### 3.1 Authentication & Session Subsystem

- **Standalone Auth**: The Katara backend exposes `/api/v1/auth/register`, `/api/v1/auth/login`, `/api/v1/auth/me`, `/api/v1/auth/logout`.
- Passwords are encrypted using `bcrypt` and stored in `katara_db.users`.
- The backend issues signed HMAC-SHA256 JWT tokens with a 7-day expiration.
- The Next.js BFF proxy stores the token in an `httpOnly`, `SameSite=Lax` cookie named `auth_token` and automatically injects `Authorization: Bearer <token>` when proxying requests to port 8090.

### 3.2 Ingestion & Semantic Pipeline

1. User uploads document (PDF / Markdown / Text) via `/api/v1/katara/sources`.
2. Source payload is stored in GarageHQ S3 bucket (`inquizitive-docs`).
3. An ingestion task is enqueued to Redis via Asynq.
4. Asynq worker parses content into semantic blocks (300-500 tokens).
5. AI extracts atomic flashcards with archetype (`conceptual`, `procedural`, `scenario`), domain, sub-topic, and keypoints.
6. Dense vector embeddings are generated and stored in Qdrant collection `katara_flashcards`.
7. Flashcards and initial FSRS records (`katara_srs_states`) are saved to PostgreSQL `katara_db`.

### 3.3 Adaptive Drill & FSRS Scheduler

- **Daily Mix Algorithm**: 70% due cards (FSRS review intervals) + 30% new unlearned cards.
- **LLM Variation**: Questions are dynamically generated by LLM (MCQ with distractor traps, True/False, Short Answer, or Scenario case study).
- **Evaluation & Hesitation Tracking**:
  - Latency is recorded in milliseconds and clamped to `[0, 1800000]` ms (0 to 30 min).
  - Responses are classified into `mastered` (< 30s & correct), `hesitant` (> 30s & correct), or `impulsive` (< 5s & incorrect).
  - FSRS parameters (`stability`, `difficulty`, `reps`, `lapses`, `due_at`) update immediately.

## 4. Key Architecture Decision Records (ADR Summary)

| ADR         | Title                             | Decision                                                                                                |
| ----------- | --------------------------------- | ------------------------------------------------------------------------------------------------------- |
| **ADR-001** | Qdrant as Exclusive Vector Store  | Flashcard vectors stored only in Qdrant; no SQL ILIKE fallback.                                         |
| **ADR-004** | Standalone Katara Backend Service | Katara runs its own Go Fiber service (`katara-backend`, port 8090) with its own database (`katara_db`). |
| **ADR-005** | Standalone Monorepo App Directory | Entire Katara codebase is organized under `app/KataraGnosis/{frontend,backend}`.                        |
| **ADR-009** | Standalone Katara Authentication  | Katara backend manages its own `users` table and JWT issuance independent of Echo.                      |
